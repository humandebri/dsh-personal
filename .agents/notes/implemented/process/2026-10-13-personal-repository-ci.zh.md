# Agent Note: 个人 DSH 仓库的 CI

Status: implemented

[English](2026-10-13-personal-repository-ci.md) | 中文

## 问题

个人仓库继承了组织专用的运行器标签、Issue Project 自动化、发布系列检查及需要凭据的工作流。这些服务没有在 `humandebri/dsh-personal` 中配置，因此继承的 PR 检查会等待不可用的运行器，或在验证代码之前失败。

## 决策

个人仓库的每个必需 CI 作业使用 GitHub 托管的 Ubuntu 和 Windows 运行器。作业命令、依赖关系及失败传播保持完整。其他仓库现有的运行器选择保持不变。

Issue policy 检出默认分支的可信代码，并在预检之前仅按已知个人仓库身份改写 REST 查询的仓库命名空间。策略适用条件、当前状态复核及 Project 凭据要求保持完整。组织 Project 生命周期及上游 npm 发布演练不在个人仓库中运行；该仓库不发布上游发布系列。本地包仍遵循普通静态 CI 强制检查的根版本、工作区依赖范围和发布文件约束。

真实提供方 E2E 需要 `DSH_PERSONAL_REAL_API_E2E=true`；启用后仍须提供现有 API 密钥，并排除 fork 和 Dependabot PR。Cloudflare 预览需要 `DSH_PERSONAL_CLOUDFLARE_PREVIEW=true` 及现有部署凭据。未启用的作业属于跳过，不代表 API 调用或部署成功。无密钥的单元、浏览器、兼容性、覆盖率及产物检查继续运行。

干净检出验证还修复了现有个人扩展的集成遗漏：拆分 Host/Client 项目引用、分类目录类型和服务角色、根据已提交源码重新生成文档、使用有类型的测试替身，以及共享队列渲染和附件读取。共享队列在保存未完成时拒绝重复提交；多行编辑和提示浮层保留主输入区行为。

## 后果

个人 PR 能在没有上游基础设施的情况下验证代码。需要审查且包含解决 Issue 引用的 PR 仍须具有有效 Project 配置；本改动不创建个人 Project 或其 App 凭据。GitHub 托管运行器的容量小于上游运行器，因此完整 CI 可能耗时更长。

## 考虑过的替代方案

**使用继承的组织服务。** 个人仓库无法访问其运行器和凭据。

**禁用代码检查。** 这会掩盖回归，而不是修复执行环境。

## 验证

工作流测试验证个人运行器选择、依赖密钥的启用开关及 fork 限制，并保留上游测试场景。Issue 策略测试分别使用个人、上游及无关仓库身份执行工作流脚本，证明仅个人命名空间发生变化且可信策略代码保持不变。合并前以真实 Actions 结果验证安装、执行和必需作业的完成状态。
